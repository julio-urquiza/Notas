# El problema de usar Mongoose directamente en todos lados

Lo mostrado antes es una forma común para aprender o para proyectos pequeños/medianos, pero en proyectos más profesionales normalmente se intenta desacoplar la aplicación de la base de datos.

Porque si mañana querés cambiar:

* MongoDB → PostgreSQL
* MongoDB → MySQL
* MongoDB → Redis
* etc.

no querés reescribir toda la aplicación.

Muchos hacen esto:

```js
import User from '../models/User'

const getUsers = async () => {
  return await User.find();
};
```

El problema:

```txt
Service -> depende directamente de Mongoose
```

Entonces toda tu lógica queda atada a MongoDB.

---

# En arquitectura más profesional

Se suele usar:

```txt
Controller
   ↓
Service
   ↓
Repository / DAO
   ↓
Database
```

La idea es:

* el service NO sabe si usás MongoDB
* el service NO sabe si usás PostgreSQL
* solo sabe que existe algo que obtiene usuarios

---

# Ejemplo profesional

## Service

```js
class UserService {
  constructor(userRepository) {
    this.userRepository = userRepository;
  }

  async getUsers() {
    return await this.userRepository.findAll();
  }
}
```

Fijate que:

```txt
NO usa mongoose
NO usa SQL
NO sabe la DB
```

---

# Repository MongoDB

```js
class MongoUserRepository {
  async findAll() {
    return await UserModel.find();
  }
}
```

---

# Repository PostgreSQL

```js
class PostgresUserRepository {
  async findAll() {
    return await db.query('SELECT * FROM users');
  }
}
```

---

# El service no cambia

```js
const service = new UserService(new MongoUserRepository());
```

o

```js
const service = new UserService(new PostgresUserRepository());
```

La lógica sigue funcionando.

---

# Esto es inversión de dependencias

Muy importante para una arquitectura profesional.

La aplicación depende de abstracciones:

```txt
UserRepository
```

y no de tecnologías concretas:

```txt
mongoose
postgres
mysql
```

---

# Entonces, ¿cómo se hace "bien"?

## Nivel inicial/intermedio

Está perfecto:

```txt
Express + Mongoose directo
```

Porque:

* más simple
* menos abstracción
* más rápido de desarrollar

---

## Nivel más profesional/escalable

Se desacopla:

```txt
Controller
Service
Repository
Database adapter
```

y normalmente:

* interfaces
* dependency injection
* repositories
* ORM/ODM abstractions

---

# Explicación conceptual

> Para aprender usamos Mongoose directamente porque simplifica mucho el trabajo con MongoDB.
> En arquitecturas más profesionales suele agregarse una capa Repository para desacoplar la lógica de negocio de la base de datos y permitir cambiar la tecnología sin modificar el resto de la aplicación.

# Algo importante

Aunque uses Repository:

```txt
SIEMPRE vas a tener que cambiar algo
```

porque MongoDB y PostgreSQL modelan datos distinto.

Pero:

* cambiás una capa
* no toda la app

Ese es el verdadero objetivo arquitectónico.

# Arquitectura aun mas profesional

```js 
import express from 'express'
import mongoose from 'mongoose'

const app = express();

mongoose.connect(process.env.MONGO_URI);

app.listen(3000);
```

Funciona, pero:

```txt
app.js conoce mongoose
```

Entonces queda acoplado.

---

# Forma más profesional

Separar:

```txt 
Application Layer
Infrastructure Layer
```

---

# Ejemplo profesional

## db.js

```js 
import mongoose from 'mongoose'

const connectMongo = async () => {
  try {
    await mongoose.connect(process.env.MONGO_URI);

    console.log('Mongo conectado');
  } catch (error) {
    console.error(error);

    process.exit(1);
  }
};

export default connectMongo;
```

---

# app.js

```js 
import express from 'express'

const app = express();

export default app;
```

---

# server.js

```js 
import dotenv from 'dotenv'
import app from'./app'
import connectMongo from './src/infrastructure/database/mongo'

await connectMongo();

app.listen(process.env.PORT, () => {
  console.log('Servidor corriendo');
});
```

---

# ¿Por qué esto es mejor?

Porque separás responsabilidades.

## app.js

Solo configura la aplicación.

---

## mongo.js

Solo sabe conectarse a MongoDB.

---

## server.js

Orquesta el arranque.

---

# Y todavía se puede abstraer más

Muy común en arquitecturas limpias.

---

# Ejemplo con Database Provider

## database/index.js

```js 
import connectMongo from './mongo'
import connectPostgres from './postgres'

const connectDatabase = async () => {
  const db = process.env.DB_DRIVER;

  switch (db) {
    case 'mongo':
      await connectMongo();
      break;

    case 'postgres':
      await connectPostgres();
      break;

    default:
      throw new Error('Database no soportada');
  }
};

export default connectDatabase;
```

---

# server.js

```js 
import connectDatabase from './database'

await connectDatabase();
```

---

# Entonces mañana cambiás

```env 
DB_DRIVER=postgres
```

y el bootstrap cambia automáticamente.

---

# Esto ya entra en arquitectura enterprise

Conceptos importantes:

| Concepto               | Objetivo                  |
| ---------------------- | ------------------------- |
| Separation of concerns | separar responsabilidades |
| Dependency inversion   | depender de abstracciones |
| Infrastructure layer   | aislar tecnologías        |
| Bootstrap layer        | inicializar recursos      |
| Composition root       | ensamblar dependencias    |

---

# Algo MUY importante para explicar

Aunque abstraigas la conexión:

```txt 
la infraestructura SIEMPRE existe
```

No desaparece MongoDB.

Simplemente:

* la encapsulás
* reducís acoplamiento
* centralizás cambios

# Explicacion conceptual

> En aplicaciones pequeñas la conexión suele hacerse directamente en `app.js`.
> En arquitecturas más profesionales se abstrae en una capa de infraestructura para desacoplar la aplicación de la tecnología de base de datos y centralizar la inicialización del sistema.
