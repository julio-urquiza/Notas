La **estructura básica** de un archivo `config.yml` en **Artillery** se divide en dos partes principales:

1. **`config`** → define parámetros globales de la prueba (target, fases de carga, etc.).
2. **`scenarios`** → define qué acciones van a realizar los usuarios simulados (GET, POST, etc.).

---

### Ejemplo mínimo de `config.yml`

```yaml
config:
  target: "http://localhost:3000"   # Dirección de la API o app a probar
  phases:
    - duration: 60                  # Duración de la fase en segundos
      arrivalRate: 5                # Usuarios nuevos por segundo
  defaults:
    headers:
      Content-Type: "application/json"  # Headers por defecto

scenarios:
  - name: "Obtener lista de usuarios"
    flow:
      - get:
          url: "/api/users"
```

---

### Explicación de cada sección

#### 🔹 `config`

- **`target`** → URL base del sistema bajo prueba.
- **`phases`** → define cómo evoluciona la carga:
    - `duration`: tiempo (en segundos).
    - `arrivalRate`: cantidad de usuarios nuevos por segundo.
    - Opcionalmente: `rampTo` (para incrementar progresivamente usuarios).
- **`defaults`** (opcional) → headers o parámetros que se aplican a todas las requests.

---

#### 🔹 `scenarios`

Cada escenario representa un **flujo de usuario simulado**:

- **`name`** → nombre descriptivo.
- **`flow`** → lista de pasos que el usuario sigue:
    - `get` → petición GET.
    - `post` → petición POST (se le pasa `json` o `body`).
    - `think` → pausa (simula el tiempo de espera de un usuario).

Ejemplo con varios pasos:

```yaml
scenarios:
  - name: "Flujo de login y consulta"
    flow:
      - post:
          url: "/api/login"
          json:
            username: "test"
            password: "1234"
      - think: 2
      - get:
          url: "/api/profile"
```

---
Perfecto 🚀  
Un archivo `config.yml` de **Artillery** en modo avanzado puede tener varias secciones extra además de lo básico (`config` y `scenarios`). Esto permite: múltiples fases, payloads de datos, funciones JS personalizadas, hooks, reportes, etc.

---

## 🏗️ Estructura avanzada

```yaml
config:
  target: "http://localhost:3000"

  phases:
    - duration: 60
      arrivalRate: 5
      name: "Calentamiento"
    - duration: 120
      arrivalRate: 10
      rampTo: 50
      name: "Escalado progresivo"
    - duration: 60
      arrivalRate: 100
      name: "Pico máximo"

  payload:
    path: "./users.csv"     # CSV con datos de prueba
    fields:
      - "username"
      - "password"

  processor: "./functions.js"   # Funciones JS personalizadas

  defaults:
    headers:
      Content-Type: "application/json"

  plugins:
    publish-metrics:            # Ejemplo: enviar métricas en tiempo real
      - type: "influxdb"
        url: "http://localhost:8086"
        database: "artillery"

scenarios:
  - name: "Flujo de login y consulta"
    weight: 70                 # probabilidad de que se use este escenario
    flow:
      - post:
          url: "/api/login"
          json:
            username: "{{ username }}"   # tomado del payload CSV
            password: "{{ password }}"
          capture:
            - json: "$.token"
              as: "authToken"

      - think: 2

      - get:
          url: "/api/profile"
          headers:
            Authorization: "Bearer {{ authToken }}"

  - name: "Flujo de navegación pública"
    weight: 30
    flow:
      - get:
          url: "/api/posts"
      - get:
          url: "/api/posts/123"
```

---

## 🔎 Explicación de las secciones avanzadas

- **`phases`**:
    - `name` → etiqueta descriptiva.
    - `rampTo` → permite aumentar progresivamente la carga.
    - Se pueden definir varias fases seguidas.
- **`payload`**:
    - Carga datos de prueba desde un archivo CSV (ideal para logins o formularios).
    - Las variables se usan con `{{ variable }}`.
- **`processor`**:
    - Archivo JS externo donde defines funciones personalizadas.
    - Ejemplo: generar tokens, fechas dinámicas, randomizar datos.
- **`plugins`**:
    - Extienden la funcionalidad: métricas en InfluxDB, Datadog, reportes, etc.
- **`weight`**:
    - Permite balancear cuántos usuarios siguen cada escenario.
- **`capture`**:
    - Guarda valores de la respuesta (ej: token JWT) para usarlos después.
- **`think`**:
    - Simula pausas de usuario humano entre requests.
