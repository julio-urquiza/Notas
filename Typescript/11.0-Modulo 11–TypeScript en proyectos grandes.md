## Objetivo real

Cuando un proyecto crece, los problemas no son:

- la sintaxis
    
- los tipos básicos
    

Los problemas reales son:

- desorden
    
- imports largos
    
- tipos duplicados
    
- capas mezcladas
    
- nadie sabe dónde tocar
    

Este módulo apunta a **evitar eso**.

---

## 1. Estructura de carpetas (la base de todo)

### Estructura típica mala (muy común)

```txt
src/
  user.controller.ts
  user.service.ts
  user.repository.ts
  product.controller.ts
  utils.ts
  types.ts
```

Problemas:

- todo mezclado
    
- tipos globales sin contexto
    
- difícil escalar
    

---

### Estructura recomendada (por dominio)

```txt
src/
  modules/
    user/
      user.controller.ts
      user.service.ts
      user.repository.ts
      user.types.ts
    product/
      product.controller.ts
      product.service.ts
      product.types.ts
```

### Qué significa esto

- **Dominio** = User, Product, Order, etc.
    
- Cada dominio:
    
    - tiene sus tipos
        
    - su lógica
        
    - sus contratos
        

✔ Escalable  
✔ Mantenible  
✔ Usado en empresas

---

## 2. Tipos compartidos (cuándo y dónde)

### Regla importante

> Un tipo vive **cerca de donde se usa**,  
> salvo que **sea realmente compartido**

---

### Ejemplo de tipo de dominio

```ts
// user.types.ts
export interface User {
  id: string;
  name: string;
  email: string;
}
```

- **TIPO (TypeScript)**: contrato del dominio User
    
- **RESULTADO (runtime)**: no existe
    

---

### Tipos compartidos globales

```txt
src/
  shared/
    types/
      api.ts
      pagination.ts
```

Ejemplo:

```ts
// shared/types/api.ts
export interface ApiError {
  message: string;
  code: string;
}
```

Usado en varios módulos.

---

## 3. `index.ts` como barrel file

### Problema sin barrel

```ts
import { UserService } from "../../modules/user/user.service";
import { User } from "../../modules/user/user.types";
```

- imports largos
    
- frágiles
    
- feos
    

---

### Solución: `index.ts`

```ts
// modules/user/index.ts
export * from "./user.service";
export * from "./user.types";
export * from "./user.controller";
```

---

### Uso

```ts
import { UserService, User } from "@/modules/user";
```

- **TIPO (TypeScript)**: imports claros
    
- **RESULTADO (runtime)**: mismo JS
    

✔ Muy usado en proyectos grandes

---

## 4. `paths` en `tsconfig.json`

Esto es **clave** para evitar rutas relativas.

---

### Problema

```ts
import { User } from "../../../modules/user/user.types";
```

---

### Solución con `paths`

```json
{
  "compilerOptions": {
    "baseUrl": "src",
    "paths": {
      "@/*": ["*"],
      "@modules/*": ["modules/*"],
      "@shared/*": ["shared/*"]
    }
  }
}
```

---

### Uso real

```ts
import { User } from "@modules/user";
import { ApiError } from "@shared/types/api";
```

- **TIPO (TypeScript)**: entiende las rutas
    
- **RESULTADO (runtime)**: requiere configuración en build (ts-node / bundler)
    

✔ Estándar en industria

---

## 5. Separación dominio / infraestructura

Este punto es **nivel profesional**.

---

### Dominio

- Entidades
    
- Interfaces
    
- Reglas de negocio
    
- No depende de Express ni DB
    

```ts
// domain/user.ts
export interface User {
  id: string;
  email: string;
}
```

---

### Infraestructura

- Express
    
- DB
    
- Frameworks
    
- Implementaciones concretas
    

```ts
// infrastructure/user.repository.ts
export class UserRepository {
  async findById(id: string): Promise<User | null> {
    return null;
  }
}
```

---

### Regla de oro

> El dominio **no conoce** la infraestructura  
> La infraestructura **depende** del dominio

Esto evita:

- acoplamiento
    
- refactors dolorosos
    
- tests difíciles
    

---

## 6. Flujo completo en proyecto grande

```txt
Controller (HTTP)
   ↓
Service (casos de uso)
   ↓
Domain (reglas)
   ↓
Repository (infraestructura)
```

Cada capa:

- recibe tipos claros
    
- devuelve tipos claros
    
- no mezcla responsabilidades
    

---

## 7. Errores comunes (muy reales)

❌ Tipos globales en cualquier lado  
❌ `any` “para avanzar”  
❌ imports relativos infinitos  
❌ dominio acoplado a Express  
❌ carpetas por tipo (`controllers/`, `services/`)

---

## 8. Regla mental del módulo 11

> Los tipos **definen la arquitectura**,  
> no son solo ayuda del editor.

Si el tipo está mal ubicado → el diseño está mal.
