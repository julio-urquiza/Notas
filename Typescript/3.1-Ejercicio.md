## 1. Naming: error crítico (convención + semántica)

Tu código usa:

```ts
interface product { ... }
interface digitalProduct extends product { ... }
type auditable = product & Audit
```

### Problema

En TypeScript (y en la industria en general):

- **Interfaces y types van en PascalCase**
- `product`, `digitalProduct`, `auditable` están mal nombrados

Esto **no es estético**, es semántico:

- Distingue tipos de variables
- Facilita lectura
- Evita confusiones

### Correcto

```ts
interface Product { ... }
interface DigitalProduct extends Product { ... }
type AuditableProduct = Product & Audit
```

## 2. `interface` duplicada → _declaration merging_ (error conceptual)

Tenés esto:

```ts
interface product {
    readonly id: string
    name: string
    price: number
    description?: string
}

interface product {
    productStatus: ProductStatus
}
```

### Qué está pasando realmente

TypeScript **NO pisa la interfaz**.  
Hace **declaration merging**:

```ts
interface product {
  readonly id: string
  name: string
  price: number
  description?: string
  productStatus: ProductStatus
}
```

### Por qué esto es un problema

- El merging **no es evidente a simple vista**
    
- Es fácil generar contratos incoherentes
    
- En proyectos reales **esto es una fuente de bugs**
    

📌 **Buenas prácticas**

- El _merging_ solo se usa en:
    
    - Extender tipos de librerías
        
    - Casos muy específicos
        
- **NO** para modelar dominio propio
    

👉 Acá fue un **error conceptual**, no de sintaxis.

## 3. Uso correcto de `type` para estados (bien hecho)

Esto está **perfecto**:

```ts
type ProductStatus = "ACTIVE" | "INACTIVE";
```

✔️ Literal union  
✔️ Reemplaza enums innecesarios  
✔️ Muy usado en la industria

Bien decidido.

## 4. Herencia: bien usada, pero con error de tipeo

```ts
interface digitalProduct extends product {
    dowloadUrl: string
}
```

### Problemas

1. `digitalProduct` debería ser `DigitalProduct`
    
2. `dowloadUrl` → **typo**, debería ser `downloadUrl`
    
3. Hereda de `product` mal nombrado
    

### Correcto

```ts
interface DigitalProduct extends Product {
  downloadUrl: string;
}
```

## 5. Auditoría: bien planteada, pero mal nombrada

Esto está **conceptualmente bien**:

```ts
interface Audit {
  createdAt: Date;
  updatedAt: Date;
}

type auditable = product & Audit
```

Errores:

- `auditable` debería ser `AuditableProduct`
    
- `product` debería ser `Product`
    

Correcto:

```ts
type AuditableProduct = Product & Audit;
```

✔️ Uso correcto de composición  
✔️ Nivel intermedio–alto

## 6. Versión corregida (modelo profesional)

Este sería el **resultado esperado del módulo**, limpio y correcto:

```ts
interface Product {
  readonly id: string;
  name: string;
  price: number;
  description?: string;
  status: ProductStatus;
}

type ProductStatus = "ACTIVE" | "INACTIVE";

interface DigitalProduct extends Product {
  downloadUrl: string;
}

interface Audit {
  createdAt: Date;
  updatedAt: Date;
}

type AuditableProduct = Product & Audit;
```
