## 1. Arrays tipados

En TypeScript, **un array siempre debe tener un tipo homogéneo**, salvo que declares explícitamente lo contrario.

### Forma recomendada (más usada)

```ts
const prices: number[] = [10, 20, 30];
```

### Forma alternativa (menos común)

```ts
const prices: Array<number> = [10, 20, 30];
```

Ambas son equivalentes. En la industria:

- Frontend → `T[]`
    
- Genéricos / librerías → `Array<T>`
    

---

### Arrays de objetos

```ts
interface User {
  id: string;
  name: string;
}

const users: User[] = [];
```

TypeScript ahora garantiza:

```ts
users.push({ id: "1", name: "Juan" }); // OK
users.push({ id: "2" });               // Error
```

---

### Arrays con union types

```ts
const values: (string | number)[] = [1, "hola", 2];
```

⚠️ Ojo con esto: perdés información precisa y necesitás narrowing.

---

### Arrays readonly (muy buena práctica)

```ts
const roles: readonly string[] = ["ADMIN", "USER"];
```

No se puede:

```ts
roles.push("GUEST"); // Error
```

Muy usado para:

- Configuraciones
    
- Constantes
    
- Estados inmutables
    

---

## 2. Tuples

Una **tuple** es un array con:

- Longitud fija
    
- Tipos posicionales
    

```ts
const position: [number, number] = [10, 20];
```

Esto significa:

- `position[0]` → number
    
- `position[1]` → number
    
- `position[2]` → ❌ no existe
    

---

### Tuples con significado semántico

```ts
type HttpResponse = [number, string];

const response: HttpResponse = [200, "OK"];
```

Mucho más seguro que:

```ts
const response: (number | string)[] = [200, "OK"];
```

---

### Tuples con readonly (recomendado)

```ts
const rgb: readonly [number, number, number] = [255, 0, 0];
```

Evita mutaciones accidentales.

---

### Cuándo usar tuples (regla práctica)

Usalas cuando:

- El orden importa
    
- Hay pocos elementos
    
- Cada posición tiene un significado fijo
    

Ejemplos reales:

- Coordenadas
    
- Resultados `[error, data]`
    
- `[statusCode, payload]`
    

---

## 3. Enums

### Enum clásico (NO recomendado)

```ts
enum Role {
  ADMIN,
  USER
}
```

Problemas:

- Se transpila a JS
    
- Valores numéricos implícitos
    
- Debugging confuso
    

---

### Enum profesional (string enum)

```ts
enum Role {
  ADMIN = "ADMIN",
  USER = "USER"
}
```

Ventajas:

- Legible
    
- Seguro
    
- Valores explícitos
    

---

### Uso típico

```ts
interface User {
  id: string;
  role: Role;
}

const user: User = {
  id: "1",
  role: Role.ADMIN
};
```

---

## 4. Alternativa moderna a enums (MUY usada)

En muchos equipos **NO se usan enums**. Se prefiere esto:

```ts
const ROLES = {
  ADMIN: "ADMIN",
  USER: "USER"
} as const;

type Role = typeof ROLES[keyof typeof ROLES];
```

Esto produce:

```ts
type Role = "ADMIN" | "USER";
```

Ventajas:

- No genera JS extra
    
- Más compatible con JSON / APIs
    
- Mejor tree-shaking
    

📌 En frontend moderno, **esto es más común que enums**.

---

## Comparación rápida

|Opción|Recomendación|
|---|---|
|`enum` numérico|❌ Evitar|
|`enum` string|✅ Aceptable|
|Union de strings|✅ Muy recomendado|
|`as const` + type|✅ Profesional|
