## Objetivo real del módulo

👉 Usar clases **como contratos y unidades de diseño**,  
no como simples contenedores de funciones.

TypeScript **no inventa POO**, pero:

- La **refuerza**
    
- La **hace verificable**
    
- Evita errores que en JS aparecen en runtime
    

---

## 1. Clases tipadas (lo básico, pero bien hecho)

```ts
class User {
  id: string;
  name: string;

  constructor(id: string, name: string) {
    this.id = id;
    this.name = name;
  }
}
```

Esto ya te da:

- Tipado en propiedades
    
- Tipado en constructor
    
- Autocompletado
    
- Errores en compilación
    

---

### Forma profesional (más común)

```ts
class User {
  constructor(
    public readonly id: string,
    public name: string
  ) {}
}
```

Qué está pasando acá:

- `public` crea la propiedad automáticamente
    
- `readonly` impide reasignación
    
- Menos código, mismo resultado
    

---

## 2. Modificadores de acceso

TypeScript **sí hace cumplir** esto (a diferencia de JS puro).

### `public` (default)

```ts
class A {
  public x = 1;
}
```

Accesible desde cualquier lado.

---

### `private`

```ts
class A {
  private secret = "123";
}
```

- Solo accesible dentro de la clase
    
- Ni siquiera subclasses pueden acceder
    

---

### `protected`

```ts
class A {
  protected value = 10;
}

class B extends A {
  print() {
    console.log(this.value); // OK
  }
}
```

- Accesible en la clase y en herencia
    
- No desde afuera
    

---

## 3. `readonly` en clases

```ts
class Product {
  readonly id: string;

  constructor(id: string) {
    this.id = id;
  }
}
```

- Se puede asignar **solo en el constructor**
    
- Ideal para IDs, timestamps, etc.

## 4. Interfaces + clases (CLAVE)

Acá empieza lo importante.

### Interface como contrato

```ts
interface Repository<T> {
  findById(id: string): Promise<T | null>;
}
```

Esto dice:

> “Cualquier repositorio que maneje `T` debe implementar este método”

---

### Implementación real

```ts
class UserRepository implements Repository<User> {
  async findById(id: string): Promise<User | null> {
    return null;
  }
}
```

TypeScript verifica:

- Que el método exista
    
- Que el tipo de retorno sea correcto
    
- Que la firma coincida EXACTAMENTE
    

---

### Error típico que TS evita

```ts
class UserRepository implements Repository<User> {
  findById(id: number): User | null {
    return null;
  }
}
```

❌ Error de compilación  
✔️ Bug evitado antes de runtime

## 5. Clases abstractas

Una **abstract class** es:

- Parcialmente implementada
    
- No instanciable
    
- Diseñada para herencia
    

---

### Ejemplo claro

```ts
abstract class BaseRepository<T> {
  abstract findById(id: string): Promise<T | null>;

  protected log(message: string) {
    console.log(message);
  }
}
```

---

### Implementación concreta

```ts
class ProductRepository extends BaseRepository<Product> {
  async findById(id: string): Promise<Product | null> {
    this.log(`Buscando producto ${id}`);
    return null;
  }
}
```

---

### Diferencia clave: interface vs abstract class

|Interface|Abstract class|
|---|---|
|Solo contrato|Contrato + lógica|
|No JS generado|Genera JS|
|Múltiple implementación|Herencia simple|
|Ideal para capas|Ideal para base común|

---

## 6. Patrón real de industria (muy usado)

```ts
interface Repository<T> {
  findById(id: string): Promise<T | null>;
}

abstract class BaseRepository<T> implements Repository<T> {
  abstract findById(id: string): Promise<T | null>;

  protected validateId(id: string) {
    if (!id) throw new Error("Invalid id");
  }
}
```

Esto:

- Centraliza lógica común
    
- Mantiene contratos claros
    
- Escala bien en equipos grandes

## 7. Regla profesional IMPORTANTÍSIMA

> **Las clases implementan interfaces,  
> no al revés.**

Y:

> **Las interfaces definen qué,  
> las clases definen cómo.**
