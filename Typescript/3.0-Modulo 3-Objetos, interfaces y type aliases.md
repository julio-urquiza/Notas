## Objetivo real del módulo

Aprender a:

- Modelar **entidades de negocio**
    
- Definir **contratos entre capas**
    
- Diseñar estructuras **claras, mantenibles y escalables**
    

Si este módulo está mal entendido:

- El proyecto se llena de `any`
    
- Aparecen bugs silenciosos
    
- TypeScript pierde sentido
    

---

## 1. Tipado de objetos (la base de todo)

En JavaScript, esto es válido:

```js
const user = {
  id: 1,
  email: "test@mail.com",
  role: "ADMIN"
};
```

Pero:

- No hay contrato
    
- Nadie garantiza que eso sea un “User”
    
- Cualquier cosa puede cambiar en runtime
    

En TypeScript **no tipamos objetos sueltos**, tipamos **formas**.

---

## 2. `interface`: el contrato de una entidad

Ejemplo base (el que pusiste, correcto):

```ts
interface User {
  id: string;
  email: string;
  role: "ADMIN" | "USER";
  isActive?: boolean;
}
```

### Qué representa esto

- Un **contrato**
    
- Una **estructura esperada**
    
- Un **modelo de dominio**
    

### Detalles importantes

- `role` es un **union type** (muy buena práctica)
    
- `isActive?` es **opcional**
    
- No hay lógica, solo **forma**
    

---

## 3. Propiedades opcionales (`?`)

```ts
isActive?: boolean;
```

Significa:

- Puede existir
    
- Puede no existir
    
- TypeScript te obliga a verificar antes de usarla
    

Ejemplo:

```ts
function printStatus(user: User) {
  if (user.isActive) {
    console.log("Usuario activo");
  }
}
```

Si no validás:

```ts
user.isActive.toString(); // error
```

👉 Esto evita bugs clásicos de `undefined`.

---

## 4. `readonly`: proteger el estado

```ts
interface User {
  readonly id: string;
  email: string;
}
```

Esto significa:

- `id` **no puede cambiar**
    
- El objeto sigue siendo mutable, pero **esa propiedad no**
    

Ejemplo:

```ts
user.id = "123"; // Error
user.email = "new@mail.com"; // OK
```

Uso típico:

- IDs
    
- Timestamps
    
- Campos generados por DB
    

---

## 5. `interface` vs `type` (pregunta clásica)

### `interface`

- Diseñada para **objetos**
    
- Se puede extender
    
- Se puede reabrir (declaration merging)
    

```ts
interface User {
  id: string;
}
```

### `type`

- Alias de cualquier tipo
    
- Puede representar:
    
    - Uniones
        
    - Intersecciones
        
    - Primitivos
        
    - Objetos
        

```ts
type UserId = string;
```

---

## 6. ¿Cuál usar en la práctica?

### Regla de industria (muy aceptada):

- **`interface`** → objetos y entidades
    
- **`type`** → uniones, helpers, DTOs, aliases
    

Ejemplo claro:

```ts
interface User {
  id: string;
  email: string;
}

type UserRole = "ADMIN" | "USER";
```

---

## 7. Extensión (herencia estructural)

Ejemplo que pusiste (correcto):

```ts
interface Admin extends User {
  permissions: string[];
}
```

Qué significa:

- `Admin` tiene **todo lo de User**
    
- Agrega su propio comportamiento estructural
    

Uso real:

- Roles
    
- Variantes de entidades
    
- Especializaciones
    

---

## 8. Composición (mejor que herencia en muchos casos)

En vez de extender, **componemos**:

```ts
interface Audit {
  createdAt: Date;
  updatedAt: Date;
}

interface User {
  id: string;
  email: string;
}

type AuditedUser = User & Audit;
```

Esto es:

- Más flexible
    
- Más reutilizable
    
- Muy usado en backends reales
    

---

## 9. Tipado estructural (concepto CLAVE)

TypeScript **no es nominal**, es **estructural**.

Esto significa:

```ts
interface User {
  id: string;
}

const obj = { id: "123", extra: true };

const user: User = obj; // válido
```

Lo importante es:

- La **forma**
    
- No el nombre del tipo
    

Esto es poderoso, pero hay que usarlo con cuidado.

---

## 10. Error común de juniors

❌ Esto:

```ts
type User = {
  id: string;
}
```

No está mal, pero:

- Perdís extension clara
    
- Perdís intención semántica
    

En dominio:

- Preferí `interface`
