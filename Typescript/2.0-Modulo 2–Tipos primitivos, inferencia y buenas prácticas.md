## Objetivo del módulo

Que entiendas **cuándo TypeScript necesita que declares tipos y cuándo no**, y que aprendas a **evitar los dos errores más comunes**:

1. Sobre-tipar todo
2. Usar `any` para “callar” al compilador

Ambos son señales de bajo seniority.

---

## 1. Tipos primitivos en TypeScript

TypeScript define los mismos primitivos que JavaScript, pero **con contratos explícitos**:

```ts
string
number
boolean
null
undefined
symbol
bigint
```

Ejemplos:

```ts
let name = "Julio";       // string
let age = 30;            // number
let isActive = true;     // boolean
```

⚠️ Importante:

- `number` cubre **enteros y decimales**
- No existe `int`, `float`, etc.


---

## 2. Inferencia automática (la regla de oro)

TypeScript **infiera tipos mejor de lo que la mayoría cree**.

```ts
let count = 10;
```

TS infiere:

```ts
let count: number
```

Si luego hacés:

```ts
count = "hola";
```

Error de compilación.

### Regla profesional clave

> **Si el tipo es obvio por el valor inicial, no lo escribas.**

Esto:

```ts
let count: number = 10;
```

No está mal, pero es **ruido innecesario**.

---

## 3. Inferencia + `const` (detalle importante)

```ts
const status = "ACTIVE";
```

TypeScript infiere:

```ts
const status: "ACTIVE"
```

No `string`, sino un **literal type**.

Esto es muy potente y se usa mucho más adelante con:

- Union types
    
- Estados
    
- Redux / stores
    
- DTOs
    

Ejemplo:

```ts
function setStatus(status: "ACTIVE" | "INACTIVE") {}
```

---

## 4. `any`: el enemigo silencioso

```ts
let data: any;
```

Esto significa:

- TS deja de verificar
    
- Perdís autocompletado
    
- Perdís seguridad
    
- Perdís refactors seguros
    

Ejemplo peligroso:

```ts
let data: any = "hola";
data.toUpperCase(); // ok
data.split();       // ok
data.nonExisting(); // también "ok"
```

👉 TypeScript **no te protege más**.

### En industria

`any` suele aparecer por:

- Apuro
    
- Falta de diseño
    
- Deuda técnica
    

---

## 5. `unknown`: el reemplazo correcto de `any`

```ts
let data: unknown;
```

Diferencia clave:

```ts
data.toUpperCase(); // ERROR
```

TypeScript te obliga a **verificar el tipo antes de usarlo**.

Ejemplo correcto:

```ts
if (typeof data === "string") {
  data.toUpperCase();
}
```

👉 `unknown` **protege los bordes del sistema**:

- Respuestas de APIs
    
- JSON externos
    
- Inputs del usuario
    

---

## 6. Comparación clara: `any` vs `unknown`

|Característica|any|unknown|
|---|---|---|
|Permite todo|Sí|No|
|Seguridad|Ninguna|Alta|
|Requiere checks|No|Sí|
|Uso profesional|❌|✅|

Regla real:

> Si no sabés el tipo, usá `unknown`, nunca `any`.

---

## 7. `void`: cuando una función no devuelve nada

```ts
function logMessage(message: string): void {
  console.log(message);
}
```

- `void` indica **intención**
    
- No significa que no haya `return`, sino que **no importa el valor**
    

En funciones async:

```ts
async function save(): Promise<void> {
  // side effects
}
```

---

## 8. `never`: esto NO vuelve nunca

`never` indica que algo:

- Lanza un error
    
- Entra en un loop infinito
    
- Es un estado imposible
    

Ejemplo:

```ts
function throwError(message: string): never {
  throw new Error(message);
}
```

Uso avanzado (muy profesional):

```ts
function exhaustiveCheck(value: never): never {
  throw new Error("Unhandled case");
}
```

Esto se usa para:

- Validar `switch`
    
- Detectar estados no cubiertos
    
- Código robusto a futuro
    

---

## 9. Buenas prácticas reales (nivel empresa)

✔️ Dejar que TS infiera variables locales  
✔️ Tipar funciones (params y retornos)  
✔️ Usar `unknown` en inputs externos  
❌ Evitar `any`  
❌ No “pelearse” con el compilador  
❌ No desactivar `strict`
